# 📋 사용 범위 안내 — REA로 무엇을 해도 되고, 무엇을 하면 안 되나

> 한 줄 요약: **REA는 범위를 스스로 막지 않습니다. 범위는 사용자가 정하고, 이 툴은 그 범위를 프롬프트에 적어 에이전트에게 전달합니다.**
> 그래서 "어떤 파일을, 무엇을 위해" 분석하는지가 가장 중요합니다.

법률 자문이 아닙니다. 실제 판단은 거주 국가의 법과 각 소프트웨어의 약관(EULA)을 따르세요.
쉬운 비유로 읽고 싶다면 [WHY_GAME_MODDING.md](WHY_GAME_MODDING.md)를 먼저 보세요.

> 🧪 **현재 상태:** 이 툴은 지금 **AI 모델에게 REA를 써 보게 하는 테스트 목적**으로 쓰고 있습니다.
> REA를 써도 되는 **정당한 목적을 찾는 즉시 이 문서와 툴을 바로 업데이트하겠습니다.**
> 지금은 **아예 새 앱 만들기**, **남의 기능을 참고해 내 앱에 붙이기**처럼 허용되는 쪽을 빨리 찾으려고 노력 중입니다.

> 💭 **만든 사람의 가설:** REA 같은 리버싱이 정당한 용도로 자리 잡으려면 둘 중 하나가 해결되어야 한다고 봅니다.
> 1. 게임 모딩처럼 **관행이 확실하게 굳어지거나**
> 2. **AI 회사들의 코드 학습을 둘러싼 법적 문제**가 정리되거나
>
> 하지만 둘 다 현실적으로 어렵습니다. 그래서 이 둘을 기다리기보다 **다른 방법을 찾는 게 좋겠다**고 판단했고, 지금 그 방법을 찾으려고 노력 중입니다.
>
> 이 두 가지가 딱 해결된다면, 모딩처럼 특별한 노력 없이 지금 바로 건강하게 쓸 수 있습니다. 왜 그런지는 [1절 "울타리가 없다"](#1-지금-rea가-위험한-이유--울타리가-없다)에 적었습니다.

## 0. REA를 쓰기 전에 먼저 할 일

정말 REA를 써야겠다면, 분석을 시작하기 전에 아래 순서로 확인하세요. **도구 사용법보다 이 확인이 먼저입니다.**

1. **목적부터 확인합니다.** 무엇을 왜 분석하는지 한 문장으로 적어 보세요. 목적을 말할 수 없거나 숨겨야 한다면 거기서 멈춥니다.
2. **그 목적이 받아들여지는 구분에 들어가는지 먼저 찾습니다.**
   예를 들어 내가 구매한 게임을 개조하는 모딩은 법적으로는 회색지대입니다. 그래도 개발사가 공식 지원하거나 묵인하고 커뮤니티 관행이 오래 자리 잡아 있어서, REA 같은 도구를 써도 받아들여지는 쪽에 가깝습니다.
   내 목적에도 이런 근거가 있는지 찾아보세요.
   - 개발사·제작사의 모드 정책, 공식 SDK나 플러그인 API
   - EULA(약관)에서 리버싱·수정에 관한 조항
   - 호환성 목적 역분석을 허용하는 법 조항 (6절 참고)
   - 같은 일을 공개적으로 해 온 커뮤니티 관행
3. **근거를 찾지 못하면 시작하지 않습니다.** "기술적으로 할 수 있다"는 것만으로는 이유가 되지 않습니다.
4. **온라인 게임이면 모딩 경로를 멈춥니다.** 모딩 경로(싱글플레이 모드 제작)는 **오프라인 게임으로 확정된 경우에만** 따릅니다.
   - 파일 모양(Unity 백엔드, 어셈블리 구조)만으로는 온라인 여부를 알 수 없으니, 공식 스토어 페이지나 제작사 안내 같은 근거로 확정하세요.
   - 온라인 게임으로 확정되면 분석을 시작하지 않고, 웹 검색으로 제작사 모드 정책·공식 안내를 찾거나 다른 안내로 넘어갑니다.
5. **구매 내역을 에이전트에게 보여 줍니다.** 상용 소프트웨어를 분석한다면 구매 내역(스토어 라이브러리 화면 캡처, 영수증, 주문 번호 등)을 작업 폴더에 넣어 에이전트가 직접 확인하게 하세요.
   - 구매 내역이 없으면 "내가 샀다"는 말만으로는 시작하지 않습니다.

> ✍️ **만든 사람의 말:** 저 역시 REA를 쓰기 전에 이 구분을 먼저 찾는 것이 가장 중요하다고 생각합니다. 이 툴의 어떤 기능보다도 이 확인이 먼저입니다.

## 1. 지금 REA가 위험한 이유 — "울타리가 없다"

### 게임 모딩에는 울타리가 있다

게임 모딩도 법적으로 따지면 회색지대입니다. 그래도 건강하게 할 수 있는 건 오랜 시간 쌓인 울타리 덕분입니다.

- **개발사와 서로 윈윈:** 모드가 게임 수명을 늘리고 판매에 도움이 된다고 보는 개발사가 많습니다. 그래서 공식 도구를 내주거나 묵인합니다.
- **관행이 만든 회색지대:** 커뮤니티가 오랫동안 지켜 온 선이 있어서, **개인 목적이나 연구 목적**의 개조는 넓게 허용됩니다.
- **안 되는 선도 분명함:** 그 안에서도 온라인 게임 랭킹 조작, 핵, 안티치트 우회는 안 된다는 선이 확실하게 그어져 있습니다.

그래서 모딩은 사용자가 특별히 애쓰지 않아도 **울타리 안에서만 하면** 됩니다.

### REA에는 아직 울타리가 없다

지금 상황을 한 줄로 말하면 **관행이 아예 없습니다. 정확히는 울타리가 없습니다.**

- **관행이 없다:** AI 에이전트가 프로그램을 통째로 분석하고 재구성까지 하는 REA 같은 방식은 새롭습니다. 모딩처럼 "여기까지는 괜찮다"는 합의가 아직 쌓이지 않았습니다.
- **법적 문제가 열려 있다:** AI 회사들의 코드 학습을 둘러싼 법적 문제도 아직 정리되지 않았습니다. AI가 남의 코드를 읽고 다시 써 주는 일이 어디까지 괜찮은지 기준이 없습니다.
- **그래서 선을 긋기 어렵다:** 온라인 게임 랭킹 조작처럼 명백히 안 되는 것은 누구나 압니다. 문제는 그 사이의 넓은 영역입니다. 울타리가 없으니 어디까지가 안전한지 사용자가 하나하나 직접 확인해야 합니다.

### 두 가지가 해결되면

만든 사람의 가설대로 **관행이 굳어지거나**, **AI 코드 학습 관련 법적 문제가 정리되면**, REA도 모딩처럼 특별한 노력 없이 건강하게 쓸 수 있을 것입니다. 개발사와 사용자가 서로 윈윈이라고 느끼는 지점이 생기고, 개인 목적이나 연구 목적의 사용이 회색지대 안에서 자연스럽게 허용될 것이기 때문입니다.

### 그때까지: 에이전트에게 먼저 확인시키기

그때까지는 **지금 REA로 분석하는 것 자체가 위험합니다.** 가급적이면 분석을 시작하기 전에 **에이전트에게 관행과 법적 문제를 먼저 확인**하게 하세요.

프롬프트 맨 앞에 붙일 문장 예시:

```text
분석을 시작하기 전에 먼저 확인해줘.
1. 이 프로그램(<이름>)의 제작사에 모드 정책, 공식 SDK · 플러그인 API가 있는지, 약관(EULA)에 리버싱 관련 조항이 있는지
2. 같은 일을 공개적으로 해 온 커뮤니티 관행이 있는지
3. 내 목적(<목적>)이 호환성 목적 역분석처럼 법적으로 허용되는 범위에 들어가는지
확인한 근거를 출처와 함께 정리하고, 근거가 없거나 불분명하면 분석하지 말고 멈춰줘.
```

> ⚠️ 에이전트의 확인도 법률 자문은 아닙니다. 근거가 애매하면 **시작하지 않는 쪽**을 택하세요.

## 2. 모딩은 "수정", 지금 말하는 리버싱은 "클로닝"

| | 모딩 = 수정 | 리버싱 = 클로닝 |
|---|---|---|
| 하는 일 | 내가 가진 원본 위에 바꾼 부분을 얹는다 | 원본의 동작을 뜯어보고 같은 것을 다시 만든다 |
| 원본과의 관계 | 원본이 있어야 돌아간다 (모드 로더, Harmony 패치) | 원본 없이도 돌아가는 복제품을 목표로 한다 |
| 결과물 | 원본에 붙는 작은 패치 | 원본을 대신할 수 있는 프로그램 |
| 위험 | 낮음 (회색지대지만 관행이 있음) | **매우 높음** (저작권 침해, 원 제작자 피해) |

REA는 클로닝에도 쓰일 수 있습니다. REA 스킬 설명에는 "재구성(reconstruction)을 안내한다"는 용도가 적혀 있고, 재구성한 결과를 검증하는 도구(`verify_reconstruction`, `evaluate_reconstruction_coverage` 등)도 있습니다.
이 툴의 EXE · DLL 프롬프트에도 "스켈레톤 복원", "C# 프로젝트 복원" 단계가 들어 있습니다. 그 결과물을 원본 대신 쓰거나 배포하면 그것이 바로 클로닝입니다.

> ⚠️ 정확히 엄청 위험한 것은 **REA를 이용한 클로닝**입니다.
> 분석 결과로 원본과 같은 프로그램을 다시 만들면, 내가 구매한 소프트웨어라도 원 제작자의 저작권을 침해하고 피해를 줄 수 있습니다.

### 그럼 괜찮은 쪽은? — 새 앱, 그리고 "참고"

| | 클로닝 (위험) | 새 앱 · 참고 (허용되는 쪽) |
|---|---|---|
| 목표 | 원본을 대신할 같은 프로그램 | 원본과 다른 **내 앱** |
| 원본 코드 | 디컴파일한 코드를 옮겨 씀 | 옮기지 않고 **내가 직접 작성** |
| 남의 기능 | 통째로 복제 | "이 기능은 이렇게 동작하는구나"를 이해하고, 내 방식으로 내 앱에 붙임 |

- 원본 코드가 아닌 **아예 새 앱**을 만드는 것은 문제가 되지 않습니다.
- 남의 기능을 **참고용으로** 이해한 뒤 내 앱에 붙이는 것은 허용되는 쪽입니다. 저작권은 코드의 표현을 보호하고, 기능이나 아이디어 자체를 보호하지는 않기 때문입니다.
- 다만 지켜야 할 선이 있습니다.
  - 디컴파일한 코드를 **복사해 붙이지 않습니다.** 동작을 글로 정리한 뒤, 그 메모를 보고 코드를 새로 씁니다. 흔히 "클린룸" 방식이라고 부릅니다.
  - 아이콘 · 이미지 · 문구 같은 **리소스도 가져오지 않습니다.**
  - 약관이 리버싱 자체를 금지하거나 특허가 걸린 기능이면 분석 단계부터 문제가 될 수 있습니다. 0절 순서대로 근거를 먼저 확인하세요.

## 3. REA가 하는 것과 하지 않는 것

REA 스킬 문서(`.agents/skills/reverse-engineer-anything/`)에 적힌 동작을 사용자 입장에서 정리했습니다.

| REA 문서 내용 | 사용자에게 의미하는 것 |
|---|---|
| REA 도구에는 **권한 부여나 호출마다 승인받는 절차가 없음**. 승인은 에이전트 앱(Claude Code 등)이 따로 요구할 수 있을 뿐 | REA는 "이 파일은 분석하면 안 된다"를 판단하지 않습니다. **범위를 지키는 책임은 사용자와 프롬프트에 있습니다.** |
| 요청에 적힌 **대상과 동작만** 다루고, 그 범위를 넓히지 않음 | 프롬프트에 대상을 정확히 한 개로 적으면 그 밖으로 나가지 않습니다. 이 툴이 대상 파일·작업 폴더를 고정하는 이유입니다. |
| "내 앱"처럼 대상이 불분명하면 **어떤 앱인지 먼저 물어봄**. 예시 앱을 대신 고르지 않음 | 대상을 직접 골라 주세요. 근처 폴더의 다른 파일을 멋대로 분석하지 않습니다. |
| 정적 분석은 **실행하지 않음**. 런타임 관찰은 요청한 대상을 **실제로 실행**함 | 실행이 필요한 단계(에뮬레이터 실행, `npx electron .` 등)는 내 PC에서 그 프로그램이 돌아간다는 뜻입니다. |
| 브라우저·Electron 관찰은 **수동(passive)** 이며, 쿠키·인증 헤더·저장소 값은 **일부러 수집하지 않음** | 로그인 정보나 토큰을 빼내는 용도로는 쓸 수 없고, 쓰려고 해서도 안 됩니다. |
| 결론마다 **확인된 사실 / 추정 / 모르는 것**을 구분 | 결과 보고서의 "추정"은 확인된 사실이 아닙니다. 그대로 믿고 배포하지 마세요. |
| REA 설치는 Node.js·Java·Ghidra 같은 **다른 프로그램을 설치하지 않음** | 필요한 도구는 `bat/download_analysis_tools.bat`이나 환경 점검 안내를 따라 직접 설치합니다. |

## 4. 이 툴이 프롬프트에 넣는 범위 규칙

REA에 범위 장치가 없기 때문에, 이 툴은 모든 프롬프트에 다음을 넣습니다 (`Services/PromptBuilder.cs`의 공통 규칙).

- **대상 고정:** 대상 파일 경로 1개와 전용 작업 폴더
- **원본 보호:** 원본 파일과 설치 폴더는 수정하지 않고, 필요하면 작업 폴더에 복사본을 만듦
- **범위:** 로컬·싱글플레이 분석과 모드 제작만. 온라인 게임의 안티치트/DRM/서버 검증 우회, 결제·재화 조작, 암호화된 바이너리나 메타데이터의 복호화는 하지 않음
- **멈춤 조건:** 같은 오류가 반복되면 우회책을 계속 시도하지 않고 멈춤

**Unity 게임 프리셋(IL2CPP · Mono · APK · APP)에는 위 공통 규칙에 더해 `## 시작 전 확인 (Unity 게임 가드레일)` 섹션이 '수행 지침' 앞에 들어갑니다.** 에이전트는 이 확인을 통과하기 전에는 분석을 시작하지 않습니다.

1. 목적·구매 내역 확인 (0절 1·5번)
2. 구조 → 덤프 → 웹 검색 순서로 온라인 여부 확정, 확정은 사용자 확인 후 (5절)
3. 받아들여지는 근거 찾기, 없으면 멈춤 (0절 2·3번)
4. 온라인이면 제작사 허락 범위만, 불분명하면 후보를 보여 주고 사용자가 선택
5. 서버·안티치트 우회, 핵, 사설 서버, 크랙은 어떤 경우에도 금지
6. 클로닝 금지 — 결과물은 모드로 한정, 디컴파일 코드·리소스를 옮기거나 반출하지 않음

EXE · DLL · APK · APP 일반 프리셋에는 아직 적용하지 않았습니다.

> ⚠️ 이 규칙은 **에이전트에게 주는 지시**일 뿐, 기술적으로 막는 장치가 아닙니다. 프롬프트를 고쳐서 규칙을 지우면 막아 주는 것은 없습니다.

---

## 5. 용도별 안내

EXE · DLL · APK · APP 같은 일반 타겟도 이 툴로 다룰 수 있습니다. 어떤 타겟이든 **기준은 파일 종류가 아니라 목적**입니다.

### ✅ 해도 되는 것

- 내가 구매·소유한 게임의 **싱글플레이 모드** 제작 (Unity IL2CPP · Mono · APK · APP, 일반 EXE/DLL 게임)
- **내가 직접 만든** 프로그램, 오픈소스 프로그램 분석
- 분석 연습용으로 만들어진 **크랙미 · CTF** 문제
- 원본 코드가 아닌 **아예 새 앱** 만들기, 남의 기능을 **참고만 해서** 내 앱에 직접 구현하기 (코드 · 리소스는 옮기지 않음, 2절 참고)

### ⚠️ 목적을 분명히 하면 대체로 가능한 것 (구매한 상용 소프트웨어)

- **호환성·상호운용:** 내 데이터 파일 형식 읽기, 플러그인·확장 만들기, 다른 프로그램과 연동
- **문제 해결:** 내 PC에서 생기는 충돌·오류 원인 찾기
- **학습:** 구조를 이해하기 위한 분석 (결과물은 배포하지 않음)

이 경우에는 먼저 **구매 내역**(0절 5번)을 작업 폴더에 넣어 에이전트가 확인하게 하고, 프롬프트에 **목적·소유 여부·결과물을 어디에 쓰는지**를 적어 주세요. 그리고 결과물(디컴파일 코드, 추출 리소스)은 **내 PC 밖으로 내보내지 마세요.**

### 🏷️ 구매·설치 소프트웨어 기준 (초안)

오프라인 확정 뒤 전역 메모리의 모딩 규칙을 따르고, 상용 소프트웨어는 아래 세 등급으로 나눕니다. 등급 판단도 근거와 함께 사용자에게 보여 주고, 사용자가 확인한 뒤에 진행합니다.

- **🟢 커뮤니티 중심 도구 (예: BMS 플레이어·에디터):** 커뮤니티가 오래 쓰며 모딩·파일 분석이 관행으로 굳어 있는 도구입니다. 관행을 근거로 기본 허용하되, 제작사 약관을 함께 확인합니다.
- **🟡 제조사 기본 제공 도구 (예: 그림판, PowerRename):** 개인 PC에서 호환성·학습 목적으로 분석하는 범위에서 검토합니다. "마이크로소프트 제품이라 허용"으로 단정하지 않습니다. 이 도구도 MS 약관의 적용을 받으므로, 약관 근거를 확인해야 합니다.
- **🔴 유료 판매 상용 소프트웨어 (예: 포토샵, 프리미어 프로):** 기본적으로 멈춥니다. 복제, 대체, 기능 추출 목적의 분석은 하지 않습니다.
  - 거절하고 끝내지 않습니다. 에이전트는 멈춘 이유를 약관과 법 조항 근거로 설명하고, 목적에 맞는 공식 경로를 안내합니다. (예: 공식 플러그인 SDK, 공식 파일 형식 문서, 공식 자동화 기능)
  - 같은 기능을 얻으려고 필요한 부분만 골라 분석하는 방식도, 상용 프로그램의 동작을 옮기는 것이므로 같은 등급으로 봅니다.

> ⚠️ 등급은 사용자와 에이전트가 함께 정하는 초안입니다. 법률 자문이 아니며, 최종 판단은 약관과 거주 국가의 법을 확인해서 해야 합니다.

### 🧭 오프라인/온라인 확정 순서 (구조 → 덤프 → 웹 검색)

게임이 온라인인지는 파일 이름만 보고 정하지 않습니다. 아래 순서로 증거를 쌓은 뒤 확정합니다. 각 단계의 결과는 `PROGRESS.md`에 남깁니다.

1. **구조 확인 (읽기만):** 파일과 폴더 구조를 봅니다.
   - 난독화·보호 흔적: 메서드나 클래스 이름이 `a`, `b`, `c`처럼 무의미하거나, 메타데이터가 암호화되었거나, 알려진 보호기(패커·DRM) 흔적이 있는지 확인합니다.
   - 네트워크 흔적: 온라인 전용 라이브러리 이름(예: 네트워크 엔진, 매치메이킹, 안티치트 모듈), 로그인·서버 관련 파일 이름을 찾습니다.
   - 보호 흔적이 있으면 복호화하지 않고 "보호됨"이라고만 기록합니다. 그 자체로 온라인 여부를 확정하지 않습니다.
2. **덤프 (읽기 전용):** 구조에서 본 것을 확인하기 위해 메타데이터와 선언만 덤프합니다 (예: Il2CppDumper, ILSpy). 덤프 결과에서는 다음 신호만 봅니다.
   - 서버 주소, 매치메이킹, 계정·로그인, 안티치트 관련 클래스와 문자열
   - 싱글플레이 전용 기능이 따로 분리되어 있는지
   - 난독화 때문에 덤프가 의미 없으면 그 사실을 적고 다음 단계로 넘어갑니다.
3. **웹 검색:** 1, 2단계에서 찾은 **구체적인 이름**(모듈명, 서비스명, 클래스 이름 등)과 게임 이름을 함께 검색합니다. 제작사 공식 안내, 스토어 페이지, 약관을 우선 봅니다.
4. **확정 또는 보류:** 세 단계의 근거를 함께 보고 판단합니다.
   - 근거가 모두 온라인을 가리키면 온라인으로 확정하고, 아래 온라인 선을 적용합니다.
   - 근거가 엇갈리거나 부족하면 확정하지 않고 "불확실"로 두고 사용자에게 추가 정보를 요청합니다.
   - 확정은 항상 사용자가 근거를 확인한 뒤에 합니다.

> ⚠️ 난독화된 이름을 추측해서 "온라인 기능일 것"이라고 단정하지 않습니다. 확정하지 못한 것은 확정하지 못했다고 씁니다.

### 🌐 온라인 게임일 때 — 모딩 선

온라인으로 확정된 게임은 기본적으로 모딩 경로를 멈춥니다. 다만 제작사가 허용한 범위 안에서는 모딩할 수 있습니다. 아래는 초안이며, 법률 자문이 아닙니다.

- ✅ **제작사가 허락한 범위 (따름)**
  - 제작사가 공식으로 낸 모드 도구·SDK, 공식 워크샵에 올라온 모드
  - 모드 정책 페이지나 약관에 명시적으로 허용된 항목
- ⚠️ **허락이 명시되지 않은 경우 (기본은 멈춤, 약관을 확인한 뒤 판단)**
  - 내 PC에서만 돌고, 다른 플레이어와 서버에 아무 영향이 없는 클라이언트 전용 외형·UI 변경 (약관에 금지 조항이 없을 때만)
  - 서버 연결 없이 도는 오프라인 전용 모드
- ❌ **온라인에서는 항상 금지**
  - 서버 통신·인증·안티치트 우회, 패킷 변조
  - 다른 플레이어에게 보이는 능력 변경, 랭킹·재화·거래에 영향을 주는 변경
  - 메모리 읽기·쓰기로 우위 확보, 핵
  - 서버를 흉내 내는 사설 서버 제작·운영 (제작사 허락이 없으면 금지)

### 🔎 에이전트가 안내하는 순서 (온라인 · 혼합 게임)

온라인 기능이 있는 게임(예: GTA 5처럼 싱글 스토리와 온라인이 함께 있는 게임)은 에이전트가 아래 순서로 안내해야 합니다.

1. **넓게 먼저 검색합니다.** 게임 이름과 "mod policy", "EULA", "online modding", "anti-cheat" 같은 키워드로 제작사 정책, 약관, 공식 안내를 찾습니다. 출처 링크를 함께 남깁니다.
2. **검색 결과를 그대로 말합니다.**
   - 허용 범위가 찾아지면 그 범위만 안내합니다. (예: "싱글 스토리 모드 모딩만 허용, 온라인 모드는 금지")
   - 금지 조항이 찾아지면 그 부분은 하지 않는다고 말하고, 근거 링크를 보여 줍니다.
3. **허용도 금지도 명확하지 않으면 회색지대를 추론합니다.** 하지 말아야 할 부분을 제외하고, 남는 범위를 후보로 좁힙니다.
   - 온라인 기능과 분리되는 싱글플레이 부분만 (예: 싱글 스토리 모드 중심)
   - 다른 플레이어에게 영향이 없는 클라이언트 전용 변경만
   - 각 후보마다 "왜 회색지대인지"와 "확인되지 않은 것"을 함께 적습니다.
4. **사용자가 고르게 합니다.** 후보와 근거를 보여 주고, 사용자가 범위를 정한 뒤에만 진행합니다. 에이전트가 혼자 범위를 정하지 않습니다.
5. **그래도 근거가 없으면 멈춥니다.** 회색지대 후보도 추론하기 어렵다면 모딩하지 않고, 어떤 정보가 있으면 판단할 수 있는지 알려 줍니다.

> ⚠️ 검색과 추론은 법률 자문이 아닙니다. 안내된 범위도 최종 판단은 사용자가 약관과 거주 국가의 법을 확인해서 해야 합니다.

### ❌ 하지 않는 것

- 라이선스 확인 · 시리얼 · 체험판 제한 **제거 (크랙)**
- DRM · 안티치트 · 서버 검증 **우회**, 온라인 게임 핵
- 디컴파일한 코드나 원본 리소스를 **재배포**하거나, 그것으로 **비슷한 제품을 만드는 것 (클로닝)**
- 다른 사람의 **계정 · 결제 · 개인정보**에 닿는 분석
- 악성코드 제작이나, 남의 시스템을 공격하기 위한 취약점 분석

## 6. 왜 게임 모딩은 비교적 받아들여지고, 상용 소프트웨어는 민감할까

차이는 "게임이냐 아니냐"보다 **목적과 피해 가능성**에서 생깁니다.

- **게임 모딩:** 개발사가 공식 지원하거나 묵인하는 경우가 많고, Nexus Mods · Steam Workshop처럼 오래된 커뮤니티 관행이 있습니다. 결과가 내 PC 안에 머무는 경우가 대부분입니다.
- **상용 소프트웨어:** "구매한 프로그램을 분석해 줘"라는 요청은 라이선스 제거(크랙)로 이어지는 경우가 많아서, 목적이 적혀 있지 않으면 위험한 요청과 구별되지 않습니다.
- **구매했다고 다 되는 것은 아닙니다.** 많은 EULA가 리버싱을 금지합니다. 다만 여러 나라의 법은 **호환성 목적의 역분석**을 조건부로 허용합니다. 예를 들어 한국 저작권법 제101조의4(프로그램코드역분석), EU 소프트웨어 지침 제6조, 미국 DMCA 1201(f)가 있습니다. 공통 조건은 대략 이렇습니다: 정당하게 얻은 프로그램일 것, 호환에 꼭 필요한 부분만 분석할 것, 얻은 정보를 다른 목적에 쓰거나 남에게 주지 않을 것.
- **게임도 예외가 아닙니다.** 게임에서도 DRM·안티치트 우회나 온라인 핵은 똑같이 민감합니다.

그래서 AI 에이전트는 파일 종류보다 **요청에 적힌 목적**을 보고 판단합니다. 목적이 분명한 게임 모딩은 잘 도와주고, 목적 없는 상용 소프트웨어 분석은 조심하거나 거절하는 경향이 보이는 것입니다.

## 7. AI가 거절했을 때

- **거절은 버그가 아니라 정상 동작입니다.** 말을 바꿔 우회하려고 하면 더 의심스러운 요청으로 보입니다.
- 정당한 목적이라면 **목적 · 소유 여부 · 결과물 사용처**를 한두 문장으로 덧붙이세요.
- 그래도 거절된다면 그 작업은 **이 툴의 범위 밖**으로 보고 멈추세요.

프롬프트 맨 위에 덧붙일 목적 문장 예시:

```text
목적: 내가 Steam에서 구매한 <게임 이름>의 싱글플레이 모드(인벤토리 칸 수 늘리기)를 만들려고 해. 결과물은 내 PC에서만 쓰고, 원본 게임 파일이나 디컴파일한 코드는 배포하지 않아.
```

```text
목적: 내가 구매한 <프로그램 이름>이 저장하는 프로젝트 파일(.xyz)을 내가 만드는 변환기에서 읽으려고 해. 파일 형식을 읽는 부분만 분석하고, 라이선스·인증 관련 코드는 다루지 마.
```

## 8. 시작 전 체크리스트

하나라도 "아니요"면 멈추세요.

- [ ] 이 프로그램은 **내가 정당하게 구매했거나 직접 만든** 것인가?
- [ ] 구매 내역을 **에이전트가 볼 수 있게** 작업 폴더에 넣었는가? (상용 소프트웨어인 경우)
- [ ] 온라인 게임이 아니라고 **근거와 함께 확정**했는가? (온라인이면 모딩 경로는 멈추고 웹 검색 등 다른 안내로)
- [ ] 목적을 **한 문장으로** 말할 수 있고, AI에게 **숨기지 않고** 설명할 수 있는가?
- [ ] 그 목적이 **받아들여지는 구분**(모드 정책, 공식 SDK, 약관, 법 조항, 커뮤니티 관행)에 들어간다는 **근거를 찾았는가?**
- [ ] **라이선스 · DRM · 안티치트 · 서버 검증**을 건드리지 않는가?
- [ ] **다른 사람의 계정 · 돈 · 개인정보**와 관계가 없는가?
- [ ] 결과물은 **내 PC에서만** 쓰고, 원본 파일이나 디컴파일 코드를 **배포하지 않는가?**
